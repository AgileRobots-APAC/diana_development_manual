# Building and Publishing This Manual

This page is for maintainers of this manual. It explains local HTML builds, printing the current page to PDF, and GitHub Pages or GitLab Pages publication.

## Prerequisites

Use Python 3.12 or a compatible version and Git.

```bash
git clone --recurse-submodules <repository-url>
cd <repository-directory>
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

## Build HTML

Run:

```bash
make html
```

HTML output goes to `build/html/`. The Chinese and English entry points are `build/html/index.html` and `build/html/en/index.html`. Preview them locally with:

```bash
python3 -m http.server --directory build/html 8000
```

Then open `http://127.0.0.1:8000`.

### Build only some modules

All guide modules are enabled by default. Set `DIANA_BUILD_CPP`, `DIANA_BUILD_PYTHON`, `DIANA_BUILD_FCI`, or `DIANA_BUILD_ROS2` to `0` to exclude the module from both the Chinese and English sites. The two ROS 2 distributions can also be switched separately with `DIANA_BUILD_ROS2_HUMBLE` and `DIANA_BUILD_ROS2_JAZZY`. For example, hide Jazzy while its pages are unfinished:

```bash
DIANA_BUILD_ROS2_JAZZY=0 make html
```

Every build clears the old HTML, so no pages of a disabled module remain.

## Source Layout and Maintenance Rules

Chinese sources are under `docs/zh_CN/` and English sources under `docs/en/`, with identical page paths. `docs/_static/`, `docs/_templates/`, `docs/conf_common.py` and the sidebar tree `docs/navigation.py` are shared by both sites.

- Add, rename or remove a page in both languages at once, and update the toctree and `docs/navigation.py`; the build fails if a page is missing from the sidebar.
- Run `make check` before committing to verify that pages exist in pairs and have the same heading structure.
- `reference/error_codes.md` is generated by `scripts/generate_error_codes.py`; do not edit it by hand.
- The ROS 2 Humble structure diagrams and the release-baseline diagram on the Versions and Updates page are generated with Graphviz by `scripts/build_ros2_diagrams.py` and `scripts/build_release_baseline.py`; to change them, edit the script and rerun it instead of editing the PNG files.

## Theme and Build Tools

The look of the web pages (templates, colors and dark mode, the sidebar, note windows, tables, the image viewer, the version selector, and the language switch) and the tools for the versioned site build, static-file deduplication, and the bilingual parity check come from the separate theme repository `agile-docs-theme`, which sits in the `theme/` directory as a submodule. This repository keeps only what belongs to the content: the navigation structure `docs/navigation.py`, the sidebar icon configuration `docs/_static/project.js`, and the images and diagrams.

- If `theme/` is empty after cloning, run `git submodule update --init`.
- Do not edit the files in `theme/` directly; make appearance changes in the theme repository and then update the commit the submodule points to.
- See `theme/README.md` for how to use and configure the theme; other documentation projects can include it the same way.

## Print the current page to PDF

The print button in the page toolbar opens the browser print dialog for the current page. Select “Save as PDF” when a PDF is needed. CI does not pre-generate a file or build a complete-manual PDF.

## Build the versioned site and publish

`data/versions.json` defines published versions. Build the current version and every published version with:

```bash
python3 scripts/build_versioned_site.py
```

The final publication directory is `public/`: the development version sits at the site root and each registered release in its own subdirectory such as `/v1.0.0/`. A push to the default branch automatically:

1. builds bilingual HTML;
2. verifies both language entry points;
3. publishes `public/` through `.github/workflows/deploy-pages.yml` on GitHub or `.gitlab-ci.yml` on GitLab.

Both configurations can remain in the repository. GitHub ignores `.gitlab-ci.yml`, while GitLab ignores `.github/workflows/`, so the same commit can be pushed safely to both platforms.

To publish a release:

1. After the content is verified, create a Git tag that starts with `v`, for example `v1.0.0`. Do not move a published tag; for content fixes create a patch version such as `v1.0.1`.
2. Add an entry to `data/versions.json`: set `ref` to the tag, `path` to the site subdirectory, `published` to `true`, and `status` to anything other than `development`. Only registered tags are published; tags are never discovered automatically.
3. Push to the default branch. CI builds the development version and every registered tag.

Before publishing, verify that the version registry, the release baselines of each module (C++ / Python SDK, FCI, ROS 2; see [Versions and Updates](versions.md)), and the manual content match.
